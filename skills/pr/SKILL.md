# PR 올리기

목적: AI 가 만든 변경을 사람이 PR 에서 한 번 더 읽고 거를 수 있게 한다. 그래서 본문은 **AI 가 하려던 일**이 아니라 **diff 에 실제로 있는 것**을 적는다.

머지는 사람이 GitHub 에서 **Rebase and merge** 로 한다. 직접 머지하거나 `gh pr create`·`gh pr edit` 를 따로 부르지 않는다. 올리기는 `task.py pr` 만 쓴다.

아래 `task.py` 는 `python3 "<skill-dir>/../../scripts/task.py"`(프로젝트 루트에 `task.sh` 가 있으면 `./task.sh`)다. `<skill-dir>` 은 이 `SKILL.md` 가 있는 폴더다.

## 순서

1. **커밋**: 작업 폴더(`<worktrees>/<작업>/<레포>`)에서 작업에 속한 파일만 커밋한다. 미커밋 변경이 있으면 `task.py pr` 이 멈춘다.
   - 메시지는 레포의 기존 형식(`feat:`·`fix:`·`refactor:` + 한국어)으로, 무엇이 바뀌는지 쓴다.
   - PR 을 올린 뒤의 수정도 "리뷰 반영" 이 아니라 `fix: 로그인 기기 정보 빈 값 거절` 처럼 무엇을 고쳤는지 쓴다. rebase merge 라 이 커밋이 기준 브랜치에 그대로 남는다.
2. **틀 만들기**: `task.py pr <작업> --prepare` → 레포마다 `<worktrees>/<작업>/.pr/<레포>.md` 가 생기거나 파일 표가 지금 diff 로 갱신된다(이미 쓴 설명은 남는다).
3. **본문 채우기**: 출력된 커밋 목록과 `git -C <레포> diff origin/<기준>...HEAD` 를 **직접 읽고** 모든 `TODO` 를 채운다. 기억으로 쓰지 않는다.
4. **올리기**: `task.py pr <작업>`. 스크립트가 검사(필수 칸·TODO·파일 누락) → 첫 PR 이면 커밋을 하나로 합침 → push → PR 생성/갱신 → 같은 작업의 다른 레포 PR 링크까지 한다. 검사에 걸리면 아무 레포도 올라가지 않으니 고치고 다시 실행한다.
5. 결과로 나온 PR 주소를 사용자에게 알린다.

## 칸별 작성법

- **`# 제목`**: 한국어, 무엇이 바뀌는지. 첫 PR 에서는 합친 커밋의 메시지도 된다.
- **요청**: 사용자가 시킨 것 1~3줄. 사용자의 말에 가깝게.
- **요청 밖 변경**: diff 의 모든 변경을 요청과 대조해 시키지 않은 것을 적는다 — 리팩터링, 이름 바꿈, 포맷 정리, 의존성·버전, 코드 삭제, 요청과 무관한 테스트 수정. 전부 확인한 뒤에만 `없음`.
- **주의해서 볼 곳**: DB 스키마·마이그레이션, API 요청/응답 형식, 설정·환경변수, 권한·인증, 외부 호출, 삭제된 코드, 배포 때 같이 바뀌어야 하는 것. 바뀐 동작은 `기존 → 변경` 으로. 없으면 `없음`.
- **데이터 흐름**: 서비스 사이 호출 경로, 주고받는 데이터, 저장 위치(테이블·컬럼·이벤트)가 바뀔 때만 그린다. 아니면 `변경 없음` 한 줄. 여러 레포 작업이면 모든 PR 에 같은 그림을 넣는다.

  ````markdown
  ```mermaid
  sequenceDiagram
    web->>api: 로그인 요청 (deviceId 추가)
    api->>auth: POST /sessions  ★변경
    auth-->>api: 세션 토큰
  ```
  | 구간 | 기존 | 변경 |
  |---|---|---|
  | api → auth | deviceId 없음 | deviceId 필수, sessions.device_id 에 저장 |
  ````
- **파일별 변경**: 표의 파일 목록과 `+/-` 는 스크립트가 git 에서 채운다. 행마다 `무엇을 · 왜` 를 한 줄로 쓰고, 끝에 `— 요청` 또는 `— 요청 밖` 을 붙인다. 이유를 댈 수 없는 파일이 있으면 본문에 숨기지 말고 사용자에게 먼저 묻는다.
- **확인**: `함:` 실제로 실행한 명령·테스트와 결과, `못 함:` 확인하지 못한 것. 추측을 확인한 것처럼 쓰지 않는다.
- `## 이슈`, `## 커밋`, `## 관련 PR` 은 스크립트가 붙이므로 쓰지 않는다. 작업에 이슈가 있으면 PR 제목과 커밋 첫 줄 끝에 ` (이슈 ID)` 도 스크립트가 붙인다(이미 ID 가 있으면 그대로). 제목·커밋 메시지에 직접 적어도 된다.
- 본문 안에 `TODO` 라는 글자를 내용으로 쓰지 않는다(빈칸 표시로 검사한다).

## 충돌·예외

- GitHub 가 충돌을 알리면(`task.py status <작업>` 에 `CONFLICTING`): `git -C <레포> fetch origin <기준>` → `git -C <레포> rebase origin/<기준>` → 충돌 해결(양쪽 의도를 살리고 테스트를 버리지 않음) → `task.py pr <작업> --rebased`. 이때만 `--force-with-lease` push 가 된다.
- 충돌이 없는데 "원격과 갈라졌다" 로 멈추면 `--rebased` 를 붙이지 말고 원인(amend 등)을 사용자에게 알린다.
- 한 레포만 올릴 때: `--repo <레포>` (`--prepare` 에도 쓸 수 있음).
- 머지 후 정리는 `task.py done <작업>`.
